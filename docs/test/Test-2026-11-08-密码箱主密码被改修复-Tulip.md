- **日期**：2026-11-08
- **事项**：排查「密码箱主密码被改了」的反馈，修复导致密码箱密文被静默覆盖的保存机制，并加固密码输入

- **结论**：✅ 根因已定位并修复，4 个问题各自配套测试，全量测试通过，可验收

---

## 0. 现象与根因定位

**现象**：此前能解锁的主密码忽然提示「主密码不正确」，换回更早的密码反而能开。

**先排除**：全局检索确认项目里**没有自动改主密码的逻辑**。会更换 salt 的入口只有两处：

| 入口 | 位置 | 说明 |
|---|---|---|
| 设置密码箱 | `vault.js:87` `createVault()` | 仅在 `vault == null` 时出现 |
| 修改主密码 | `pages/settings.js` `changePasswordFlow()` | 必须验证当前密码通过 |

**真正根因**：数据保存是「整份覆盖 + 无并发校验」：

1. `store.js` 的 `mutate()` 在 200ms 防抖后把**整个内存 state** PUT 上去；
2. `server.js` 的 `PUT /api/data` 直接 `writeAtomic()` 覆盖，不比对版本。

于是任何持有旧快照的客户端（另一个窗口、未刷新的旧标签页、旧版前端脚本），只要保存一次账目或备忘，就会把 `state.vault`（**旧 salt + 旧密文**）一并写回文件。新主密码随之失效，旧密码「复活」——表现就是「密码被改了」。

第二条路径是「从备份恢复」：`replaceState(obj)` 会把备份里的旧 vault 一起覆盖回来，同样让主密码回退。

---

## 1. 修复一：保存并发保护（核心）

**服务端**（`server.js`）：

- 新增请求头 `X-WorkLift-Base-Updated-At`：客户端回传读取时拿到的 `updatedAt`；从未保存过传 `none`。
- 与磁盘当前 `updatedAt` 不一致 → **409**，响应体带 `conflict: true` 与最新 `updatedAt`，**不写文件**。
- 未携带该头的调用方保持原行为（200 无条件覆盖），兼容脚本与旧客户端。
- `nextUpdatedAt(prev)`：新 token 取 `max(now, prev + 1ms)`，保证严格单调——同一毫秒内连续两次写入也不会生成相同 token，校验不会形同虚设。

**前端**（`api.js` / `store.js`）：

- `saveData(obj, baseUpdatedAt)` 自动带 token（`null → none`）；409 抛出带 `conflict` 标记的错误。
- `store.js` 维护 `baseUpdatedAt`，保存成功后用服务端返回值滚动更新；**检测到冲突后暂停自动保存**，并提示「另一个窗口已更新数据，请刷新页面后再继续操作」，不再反复用旧快照撞库。
- `flushSave()`（关闭工作台前）冲突时**抛错**，宁可提示保存失败，也不静默覆盖别人的新数据。
- `replaceState()`（恢复备份/清空）属于用户二次确认后的显式覆盖，按强制模式保存。

**测试**（`test/store.test.js` 6 项 + `test/api.test.js` 7 项）：

| 用例 | 断言 |
|---|---|
| 保存带读取时的 token | PUT 头 `X-WorkLift-Base-Updated-At = 读取值` |
| 保存成功后滚动 token | 第二次保存带服务端返回的新值 |
| 409 后暂停自动保存 | `isSaveBlocked() === true`，后续 mutate 不再发请求 |
| 强制覆盖不带 token | `replaceState` 的 PUT 无 base 头 |
| 冲突时 flushSave 抛错 | `assert.rejects(/另一个窗口已更新数据/)` |
| loadData 清除冲突 | 重新加载后恢复自动保存并使用新 token |
| 过期 base → 409 | 数据文件仍是先写入者的内容，409 回传最新 token |
| token 严格递增 | 连续两次保存 `t2 > t1`，同毫秒也不同 |
| 无 base 头 → 200 | 兼容旧客户端/脚本 |
| 首次保存 `none` | 磁盘 `updatedAt=null` 时 200；重复 `none` → 409 |

## 2. 修复二：密码箱防回滚

并发校验挡住了「带 base 的旧快照」，但旧客户端（v1.3.2 前端）根本不带 base，仍能把 vault 换掉。

**规则**：`salt` 变化意味着主密码被替换。只有满足其一才允许写入：

1. 携带**有效 base**（证明客户端基于最新数据操作，属于正常「修改主密码」流程）；
2. 显式携带 `X-WorkLift-Vault-Replace: 1`（恢复备份/清空的强制覆盖）。

否则返回 **409 + `vaultConflict: true`**，密文原样保留。恢复备份流程由 `replaceState(force)` 自动带上该声明，正常改密不受影响。

**测试**（3 项）：无 base 换 salt → 409 且密文不变；显式声明 → 200；带有效 base 换 salt → 200（不误伤合法改密）。

---

## 3. 修复三：恢复备份时明确告警

恢复备份仍可能把主密码带回旧版本。现在若备份中的 vault 与当前 salt 不同，在原有两次确认之间**追加一次独立告警**：

> 备份中的密码箱与当前不一致。恢复后主密码将变回该备份创建时的密码，当前主密码会失效。

---

## 4. 修复四：密码输入本身的不一致

两种「输对了却解不开」的成因，一并处理：

| 问题 | 处理 | 兼容性 |
|---|---|---|
| 首尾空格被算进 PBKDF2，肉眼不可见 | 设置/修改时 `validateMasterPassword` 直接拒绝（含全角空格） | `unlockVault` **不 trim**，历史含空格密码仍可解锁（有专门测试构造旧格式 vault 验证） |
| 浏览器自动填充把另一个已存密码填进密码框 | 表单密码框默认 `autocomplete="new-password"`；解锁与「当前主密码」用 `off` | 仅影响新渲染的表单，不动已有数据 |

测试（`test/vault.test.js` 3 项）：首尾空格（半角/全角）拒绝、中间空格允许；`createVault`/`sealVault` 拒绝带空格；旧格式带空格密码可解锁、去掉空格解不开。

---

### 4.1 改密落盘确认（同一轮补强）

原实现中，「修改主密码」只调用 `mutate()` 改内存并立即 toast「主密码已修改」，真正落盘在 200ms 防抖之后。若这次保存被并发校验拒绝（另一个窗口刚写过），就会出现**提示已修改、磁盘仍是旧密文**的假成功——下次解锁仍是旧密码。

新增 `commitVault(nextVault, nextPassword)`：改内存 → `await flushSave()` 立即落盘 → 成功才更新会话密码；失败则回滚 `state.vault` 与 `vaultSession.password` 并把错误抛回表单。提示语只在 `await commitVault()` 之后出现。

测试（`vault.test.js` 2 项）：重新加盐后新密码可解锁且条目保留、旧密码必须失效；静态守卫校验「`flushSave` 在提示之前」「失败分支回滚密文与密码」。

## 5. 安全审计

| 检查项 | 结论 |
|---|---|
| 新增请求头注入 | 仅做字符串相等比较，不拼接 SQL/命令/路径，无注入面 |
| 跨源伪造请求头 | `X-WorkLift-*` 属自定义头，跨源必触发 CORS 预检；且中间件已校验 `Origin`/`Sec-Fetch-Site`/`Host`，外部网页无法构造 |
| 409 响应信息泄露 | 只回传 `updatedAt`（数据文件已有的时间戳），不含明文或密钥 |
| 新增读放大 | 每次 PUT 多读一次数据文件（约 270KB JSON），200ms 防抖下频率可控，不构成 DoS |
| 时间戳膨胀 | `nextUpdatedAt` 遇未来时间只 +1ms/次，不会指数增长 |
| 旧客户端兼容 | 不带头的 PUT 行为不变；带头的旧代码不存在（本轮新增） |
| 密码箱回滚 | 默认拒绝 salt 变化，仅显式声明或有效 base 放行 |

`npm audit --omit=dev` 依赖未变更（仅版本号），沿用上一轮 0 漏洞结论。

## 7. 已知边界与后续建议

- **冲突时用户需手动刷新**：本轮选择「暂停保存 + 提示刷新」，不做自动合并。自动合并需要字段级 diff，风险高于收益；刷新会丢弃当前窗口未保存的改动（提示语已说明）。
- **同一浏览器单窗口不受影响**：`loadData` 后 base 与后续保存返回值保持同步，不会误报 409。
- **未做「强制覆盖」逃生口**：冲突后只能刷新。若确有需要，可后续在提示中加「仍然覆盖」按钮，但那正是本次要消除的行为，暂不提供。
- **密码箱无找回机制**：AES-GCM 认证失败即无法解密。若历史密码确实全部遗忘，只能重置密码箱（条目丢失，其它数据不受影响）——这是加密设计的必然取舍。
